# Отчёт: «Трекер калорий» через четырёх параллельных субагентов

Дата: 24 августа 2026. Формат: соло, работа разбита на 4 независимые зоны и выполнена
четырьмя субагентами Claude Code, запущенными параллельно (`run_in_background`) в одной
координирующей сессии. Ниже — что каждый сделал, где зоны разошлись в предположениях,
сколько это стоило по времени и контексту, и что не получилось с первого раза.

---

## 1. Разбивка на зоны

| Агент | Зона (эксклюзивный доступ на запись) | Задача |
|---|---|---|
| A | `models/`, `storage/`, `api/`, `requirements.txt` | модель приёма пищи, SQLite-хранилище с атомарными операциями, CRUD API, валидация на границе |
| B | `calculations/`, `tests/test_calculations.py`, `requirements-calculations.txt` | расчёт калорий/БЖУ по весу, агрегация день/неделя, property-based тесты (hypothesis) |
| C | `frontend/` | HTML-страница: форма добавления + таблица за день |
| D | `workflows/` | workflow «дневной отчёт»: собрать → посчитать → сравнить с нормой → сохранить → пометить выполненным |

Каждому агенту явно запрещалось редактировать чужие зоны и общие файлы (`README.md`,
`REPORT.md`). После завершения всех четырёх проверено `git status --short` по корню
проекта — **границы зон не нарушены ни одним агентом**, конфликтов на уровне файлов нет.

Там, где агенту нужен был контракт из другой (параллельно пишущейся) зоны, было явно
разрешено не ждать, а зафиксировать своё предположение письменно:
`frontend/API_CONTRACT_ASSUMED.md`, `workflows/DEPENDENCIES_ASSUMED.md`. Это дало
предсказуемо неполное совпадение предположений с реальностью — разобрано в разделе 3.

---

## 2. Что сделал каждый агент

### Агент A — данные и API
FastAPI + `pydantic` для валидации на границе, `sqlite3` (stdlib) для хранения,
транзакции через контекстный менеджер (`commit`/`rollback`) + `threading.Lock` на запись,
WAL-режим. CRUD: `POST/GET/PUT/DELETE /meals`, `GET /meals/{id}`, фильтры по дате и
диапазону дат. Контракт зафиксирован в `api/API_CONTRACT.md`.

**Решение:** калории и БЖУ **вводятся вызывающей стороной напрямую** при создании записи,
а не вычисляются сервером из справочника продуктов — справочника в проекте нет, и его
создание было не в рамках задачи. Это решение задокументировано, но создало содержательный
разрыв с Агентом B (см. раздел 3.1).

**Самопроверка агента:** реально поднял `uvicorn`, прогнал через `curl` полный цикл
create → get → list (по дате и диапазону) → update → delete → 404/400 на ошибках,
проверил CORS-заголовок для `file://`-фронтенда.

### Агент B — расчёты и property-тесты
`calculations/portion.py` (расчёт порции по весу от значения на 100 г) и
`calculations/aggregation.py` (агрегация по дню и неделе). Модуль спроектирован как
самостоятельный, без импорта чужих моделей (принимает dict/duck-typed объекты) — разумное
решение в условиях параллельной работы над `models/`.

**Property-тесты (hypothesis), 5 штук — 3 обязательных + 2 бонусных:**
1. сумма агрегата за день = сумма отдельных приёмов пищи (независимый пересчёт через `math.fsum`);
2. линейность при масштабировании веса на случайное `N` (допуск на округление выведен математически, а не подобран);
3. округление никогда не даёт 0/отрицательное для положительной порции (проверено вплоть до крайне малых величин);
4. (бонус) агрегация за день не зависит от порядка приёмов пищи;
5. (бонус) `calculate_portion` не возвращает отрицательные значения для валидных входов.

**Результат прогона (перепроверено координатором):** `pytest tests/test_calculations.py -q`
→ **17 passed** (12 unit + 5 property, каждое свойство — 100–200 hypothesis-примеров).

### Агент C — фронтенд
`frontend/index.html` + `app.js` + `style.css`. Форма (продукт, вес, дата, калории, БЖУ)
и таблица за день с итоговой строкой. **Решение:** калории/БЖУ вводятся вручную для всей
порции — согласуется с решением Агента A (справочника продуктов нет).

Начал с предположения о контракте (`frontend/API_CONTRACT_ASSUMED.md`), затем, когда
`api/API_CONTRACT.md` появился, **сам подстроил** `app.js` под реальные имена полей
(`mapMealToApi`/`mapMealFromApi`) без ожидания координатора. Проверил визуально: страница
не разваливается без backend (баннер об ошибке сети, форма не теряет данные), и полный
цикл на живом mock-сервере с реальными именами полей.

### Агент D — workflow «дневной отчёт»
`workflows/daily_report.py` (stdlib только) + `workflows/config.json` (норма по умолчанию)
+ `workflows/DEPENDENCIES_ASSUMED.md`. Источник данных — `storage`/`api`/`mock` с
автоопределением; агрегация — через `calculations.aggregate_day`, с fallback-суммированием,
если модуль недоступен. Идемпотентность — sha256-хэш от (нормализованные приёмы + норма)
в `meta.combined_hash`: повторный запуск с тем же хэшем → статус `unchanged`, файл не
переписывается (проверено координатором дважды подряд на живом API — второй раз действительно
`unchanged`, mtime не менялся).

**Побочный эффект:** во время тестирования агент создал `storage/calorie_tracker.db`
(вне своей зоны на запись) и не смог его удалить из-за запрета трогать чужую зону —
корректно сообщил об этом координатору вместо того, чтобы обойти запрет. Файл удалён
координатором при сведении, `storage/*.db` добавлен в `.gitignore`.

## 3. Конфликты между зонами

### 3.1 Содержательный: расчёт «по весу» существует, но не подключён к API (главный конфликт)
Задание требовало «расчёт калорий/БЖУ по весу» — Агент B честно реализовал и протестировал
`calculate_portion(per_100g, weight_g)`. Но Агент A решил, что модель приёма пищи хранит
уже готовые калории/БЖУ (введённые вручную), а не вычисляет их из веса и справочника
продукта на 100 г — потому что справочника продуктов в проекте нет. Агент C (фронтенд)
согласованно выбрал ручной ввод.

**Итог:** `calculations/portion.py` — рабочий, протестированный, но **не используется**
в реальном пути данных API → storage → frontend. Он используется только косвенно —
агрегация по дню (`aggregate_day`, которая суммирует уже готовые калории/БЖУ) —
подключена и работает end-to-end. Расчёт «на 100 г × вес» остался изолированной,
протестированной, но не интегрированной возможностью. Это не баг координации (агенты
не могли договориться параллельно), а следствие того, что задача «расчёт по весу» на
уровне вычислений и задача «нет справочника продуктов» на уровне данных решались
независимо и разными агентами — обе по отдельности рациональны, вместе дают разрыв.
Честно фиксируем это как нерешённое, а не прячем.

**Что нужно, чтобы закрыть:** добавить (вне рамок этого прогона) минимальный справочник
продуктов «на 100 г» и точку в API/фронтенде, где выбор продукта + вес вызывает
`calculate_portion` вместо ручного ввода калорий.

### 3.2 Терминологический: имена полей
- `models/meal.py` (факт): `consumed_at`, `proteins`, `fats`.
- `calculations/aggregation.py` (предположение Агента B, не видевшего модель): `date`, `protein`, `fat`, `carbs`.
- `frontend/API_CONTRACT_ASSUMED.md` (предположение Агента C): `product`, `weight_g`, `date`, `protein`, `fat`.

**Разрешено без участия координатора:** Агент C сам переписал `app.js` под реальный
контракт до завершения своей работы; Агент D реализовал `normalize_meal()`, который
понимает оба варианта именования и адаптирует данные модели под ожидания
`calculations/`. Проверено координатором end-to-end (раздел 4) — работает.
`calculations/` осознанно не стали переписывать под имена модели, чтобы модуль оставался
самостоятельным и не зависел от `models/` — решение зафиксировано Агентом B в
`calculations/README.md`.

### 3.3 Ложный след: 500-я ошибка у API
Агент C при проверке зафиксировал, что временно запущенный на порту 8123 процесс API
отдавал `500 Internal Server Error`. При независимой проверке координатором (раздел 4)
API на том же коде работает штатно без единой ошибки — вероятно, ошибка A связана
с устаревшим/незавершённым запуском процесса в моменте, а не с багом кода. Агент C
корректно не стал чинить чужую зону и не сделал далеко идущих выводов — только сообщил
наблюдение.

## 4. Интеграционная проверка координатором (после того как все агенты вернулись)

Помимо отчётов самих агентов, координатор прогнал реальный сквозной сценарий:

1. `pip install -r requirements.txt -r requirements-calculations.txt` — без ошибок.
2. `pytest tests/test_calculations.py -q` → **17 passed**.
3. Поднят `uvicorn api.main:app --port 8000`; через `curl` создана запись, получена по дате.
4. `python workflows/daily_report.py --source api --api-base-url http://localhost:8000 --date 2026-08-24` —
   первый запуск: `recomputed`, второй запуск без изменений данных: **`unchanged`**,
   числа идентичны, файл не переписан. Идемпотентность подтверждена не на словах агента,
   а повторным запуском координатором.
5. Поднят статический сервер для `frontend/`, страница открыта в браузере поверх живого
   API (порт синхронизирован с `API_BASE_URL` в `app.js`). Через форму добавлена запись
   «Куриная грудка, 150 г»; таблица показала обе записи (включая созданную через `curl`
   «Банан») с верной итоговой строкой (270 г / 355 ккал / 47.8 Б / 5.8 Ж / 27.5 У).
   Консоль браузера — без ошибок.

Это подтверждает, что четыре независимо написанные зоны реально стыкуются в рабочую
систему, а не только «каждая часть по отдельности работает».

| Агент | Длительность | Токенов у агента | Вызовов инструментов |
|---|---|---|---|
| A — данные и API | 9 мин 13 с | ~75 200 | 28 |
| B — расчёты и тесты | 7 мин 02 с | ~67 100 | 16 |
| C — фронтенд | 21 мин 14 с | ~110 900 | 114 |
| D — workflow | 20 мин 23 с | ~109 400 | 49 |
| **Сумма (если бы делал один агент последовательно)** | **≈ 57 мин 52 с** | **≈ 362 600** | **207** |
| **Фактическое время (параллельно)** | **≈ 21 мин 14 с** (по самому долгому агенту) | — | — |

**Контекст координирующей сессии:** в главную сессию попали только четыре финальных
отчёта агентов (единицы тысяч токенов суммарно) — не 362 тысячи токенов их внутренней
работы. Это и есть эффект изоляции контекста субагентов: координатор мог параллельно
готовить структуру проекта и не держал в контексте, как каждый агент писал код.

**Наблюдение, честно контрастирующее с занятием:** на занятии на маленькой задаче
последовательный прогон был *быстрее* параллельного, а выигрыш параллельности был только
в контексте. Здесь — наоборот: параллельный прогон занял ~21 минуту против ~58 минут
при последовательном сложении, то есть выигрыш и по времени, и по контексту. Разница,
предположительно, в размере задачи: здесь у каждого агента был крупный самостоятельный
кусок (полноценный API, полноценный фронтенд) с собственным циклом самопроверки
(запуск сервера, браузер, тесты), а не короткая точечная правка — на такой доле работы
параллельность выигрывает по обоим параметрам.

## 6. Что не сделано / не сработало (честно)

- **Расчёт по весу не подключён к живому пути данных** (раздел 3.1) — главный
  содержательный пробел, не техническая недоработка, а следствие независимых
  архитектурных решений двух агентов.
- Нет UI для редактирования/удаления записей во фронтенде, хотя API это поддерживает
  (`PUT`/`DELETE /meals/{id}`) — Агент C сознательно не стал добавлять незапрошенный функционал.
- `aggregate_week` считает среднее как «сумма / 7» (календарная неделя), а не «среднее
  по дням, где были приёмы пищи» — семантика на выбор координатора, не поправлено.
- HTTP-адаптер в workflow (`urllib`, stdlib) не поддерживает пагинацию/аутентификацию —
  не нужно для текущего API, но всплывёт, если API вырастет.
- Индекс кодовой базы, оптимизатор контекста, git worktrees, инъекция недоверенного
  текста, песочница/изоляция — из необязательной части задания не пробовались в этом
  прогоне: приоритет был отдан обязательным трём пунктам с реальной интеграционной
  проверкой, а не покрытием всех бонусов.

## 7. Что засчитывается как обязательные три пункта ДЗ №2

1. **Работающий результат** — раздел 4 (реально запускается и работает сквозно, не
   «выглядит рабочим в отчёте одного агента»).
2. **Агенты: запустить и попробовать** — 4 параллельных субагента, зоны, письменно
   зафиксированные контракты вместо ожидания — разделы 1–3.
3. **Workflow** — `workflows/daily_report.py`, обязательный, идемпотентность проверена
   координатором повторным запуском, а не только заявлена агентом — раздел 4, пункт 4.
