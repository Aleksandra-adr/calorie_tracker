# Трекер калорий

Учебный проект: учёт приёмов пищи (продукт, вес, дата, калории, БЖУ), расчёт и агрегация
по дню/неделе, веб-форма с автоподстановкой по справочнику продуктов, предупреждение
о превышении дневной нормы, недельная выгрузка в CSV/PDF и повторяемый workflow дневного
отчёта.

Собран для ДЗ №2 («Агенты · Workflow · Изоляция») в пять шагов: **агенты** (4 параллельных
субагента на базовую функциональность) → **ломатель** (отдельная сессия, 22 сценария атаки)
→ **workflow** (упаковка в Claude Code skill) → **worktrees** (3 параллельные фичи в
отдельных ветках, смерженные в `master`) → **изоляция** (проверка границы песочницы).
Подробности по каждому шагу — в [`sessions/`](sessions/) (журналы сессий с промптами
дословно), полный технический разбор первого шага — в [REPORT.md](REPORT.md), итоговый
PDF-отчёт по всем пяти шагам — [`Отчёт — агенты, ломатель, workflow, worktrees,
изоляция.pdf`](<Отчёт — агенты, ломатель, workflow, worktrees, изоляция.pdf>).

## Как запустить

### 1. Установить зависимости

```bash
pip install -r requirements.txt -r requirements-calculations.txt -r requirements-weekly-export.txt
```

### 2. Запустить API

```bash
uvicorn api.main:app --reload
```

API поднимается на `http://localhost:8000`. База SQLite создаётся автоматически
в `storage/calorie_tracker.db` при первом запуске (путь переопределяется переменной
`CALORIE_TRACKER_DB`). Полный контракт эндпоинтов — [api/API_CONTRACT.md](api/API_CONTRACT.md):

- `POST/GET/PUT/DELETE /meals`, `GET /meals/{id}` — CRUD приёмов пищи;
- `GET /products?q=` — поиск по справочнику продуктов (для автоподстановки);
- `GET /products/portion?product_name=&weight_grams=` — пересчёт калорий/БЖУ по весу;
- `GET /meals/summary?date=` — итоги за день + норма + флаги превышения (`ok/near/exceeded`);
- `GET /reports/weekly?start_date=&format=csv|pdf` — недельная выгрузка;
- `GET /health` — проверка живости.

### 3. Открыть фронтенд

```bash
cd frontend
python -m http.server 8532
```

Открыть `http://localhost:8532/index.html` в браузере (API должен быть запущен на
`http://localhost:8000` — константа `API_BASE_URL` в `frontend/app.js`). Страницу можно
открыть и прямо из файла (`file://`) — она не разваливается без backend, просто показывает
баннер об отсутствии соединения. При вводе названия продукта появляется автоподстановка
из справочника; итоговая строка таблицы подсвечивается при приближении к дневной норме
или её превышении.

### 4. Прогнать тесты

```bash
pytest tests/ -v
```

**29 тестов, все зелёные:** 17 в `test_calculations.py` (12 unit + 5 property-based
на hypothesis), 10 в `test_product_catalog.py`, 2 в `test_api_error_handling.py`
(регрессия на баг с NaN/Infinity, см. ниже).

### 5. Запустить дневной отчёт (workflow)

```bash
python workflows/daily_report.py --source api --api-base-url http://localhost:8000 --date 2026-08-24
```

Повторный запуск с теми же данными даёт статус `unchanged` и не переписывает файл —
подробности в [workflows/DEPENDENCIES_ASSUMED.md](workflows/DEPENDENCIES_ASSUMED.md).
Оформлен как повторяемая процедура — [`.claude/skills/daily-calorie-report/SKILL.md`](.claude/skills/daily-calorie-report/SKILL.md).

### 6. Недельная выгрузка (CSV/PDF)

```bash
python workflows/weekly_export.py --start-date 2026-08-18 --source storage --format both
```

Файлы появляются в `workflows/output/week_<дата>.{csv,pdf}`; кириллица в PDF — через
автоопределяемый системный шрифт, с честным fallback на английские подписи, если шрифта
на машине нет.

- Поднят реальный API, через `curl`/`requests` пройден полный CRUD-цикл, поиск продукта,

- `workflows/daily_report.py --source api` запущен дважды подряд: первый раз `recomputed`,

  калорий/БЖУ по весу (200 г курицы → 330 ккал, сверено вручную), сохранение записи,
  предупреждение о превышении нормы — без ошибок в консоли.
- **После слияния трёх веток worktrees** обнаружились и были исправлены два реальных

- Баг с крахом 500 на `NaN`/`Infinity` (найден ломателем, см. ниже) — воспроизведён

## Известные проблемы (честно, не скрыто)

Отдельная сессия-«ломатель» (22 сценария атаки, [sessions/session-2.md](sessions/session-2.md))
нашла шесть проблем. Одна исправлена:

- ~~Крах 500 на `NaN`/`Infinity` в теле ошибки 422~~ — **исправлено**, см. коммит с обработчиком
  `RequestValidationError` в `api/main.py` и `tests/test_api_error_handling.py`.

Остальные пять оставлены как есть — осознанно, не забыты:

- Нет авторизации/понятия «пользователь» — архитектурный пробел, не критично для
  однопользовательского учебного проекта.
- Нет проверки правдоподобия между весом и калориями.
- Даты принимаются без разумных границ (2099, 1900, год 1).
- Type coercion: `weight_grams: true` тихо становится `1.0`.
- Дублирующиеся приёмы пищи не отслеживаются.

## Что не подключено

Расчёт «на 100 г × вес» (`calculations/portion.py`) изначально не был подключён к живому
пути данных API → storage → frontend — см. [REPORT.md, раздел 3.1](REPORT.md). Это закрыто
в ветке `feature/product-search` (сессия 4): `GET /products/portion` теперь — единственное
место, где вызывается `calculate_portion`, а автоподстановка на фронтенде идёт через этот
эндпоинт. Ручной ввод калорий/БЖУ по-прежнему поддерживается как есть, для продуктов вне
справочника.

## Замеры: последовательно против параллельно

Кроме параллельного прогона (4 субагента, см. выше), сделан отдельный **реальный**
последовательный прогон той же задачи одним агентом — [`sequential-run/`](sequential-run/)
([полный отчёт](sequential-run/REPORT.md)). Не путать с «суммой длительностей четырёх
агентов» (≈58 мин, [REPORT.md, раздел 5](<REPORT.md>)) — это сумма, а не факт: реальный
последовательный прогон занял **≈6 минут**, что почти в 3.5 раза *быстрее* параллельного
(≈21 минуту). Полный разбор и честная поправка к более раннему выводу — в
[REPORT.md, раздел 5.1](<REPORT.md>).

## Кто что делал

Всё сделано одним человеком через субагентов Claude Code (роль — разработка): 4 параллельных
агента на базовую функциональность, отдельная сессия-ломатель, 3 агента в worktrees на новые
фичи, отдельная сессия на проверку изоляции. Разбивка на зоны, сведение контрактов, слияние
веток и все интеграционные проверки — координирующей сессией (главным агентом), не по словам
субагентов на слово. Журналы всех пяти шагов с промптами дословно — в [`sessions/`](sessions/).
