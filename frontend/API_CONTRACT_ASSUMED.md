# Предполагаемый REST-контракт API (черновик от фронтенда)

Этот файл описывает контракт, который фронтенд (`frontend/`) ожидает от бэкенда.
Он написан до появления `api/API_CONTRACT.md`, потому что тот файл ещё не
существовал на момент разработки фронтенда. Если `api/API_CONTRACT.md`
появится и будет отличаться — фронтенд нужно подстроить под реальный
контракт (см. `frontend/app.js`, константы и функции `apiCreateMeal` /
`apiListMeals`, а также маппинг полей `mapMealFromApi` / `mapMealToApi`
в одном месте).

Базовый URL задаётся константой `API_BASE_URL` в `frontend/app.js`
(по умолчанию `http://localhost:8000`).

## 1. Создать приём пищи

`POST {API_BASE_URL}/meals`

Заголовки: `Content-Type: application/json`

### Тело запроса (JSON)

```json
{
  "product": "Куриная грудка отварная",
  "weight_g": 150,
  "date": "2026-08-24",
  "calories": 248,
  "protein": 46.5,
  "fat": 5.4,
  "carbs": 0
}
```

Поля:
- `product` (string, обязательное) — название продукта/блюда.
- `weight_g` (number, обязательное) — вес порции в граммах.
- `date` (string, обязательное) — дата приёма пищи в формате `YYYY-MM-DD`.
- `calories` (number, обязательное) — калорийность порции, ккал.
- `protein` (number, обязательное) — белки, г.
- `fat` (number, обязательное) — жиры, г.
- `carbs` (number, обязательное) — углеводы, г.

Калории и БЖУ вводятся пользователем вручную на фронтенде (см. пояснение
в отчёте/README фронтенда) — то есть отправляются уже посчитанными для
всей порции (не «на 100 г»).

### Ответ 201 Created

```json
{
  "id": 1,
  "product": "Куриная грудка отварная",
  "weight_g": 150,
  "date": "2026-08-24",
  "calories": 248,
  "protein": 46.5,
  "fat": 5.4,
  "carbs": 0
}
```

Сервер присваивает `id`. Остальные поля — эхо запроса (либо
перевычисленные сервером, если он решит валидировать/округлять).

### Ошибки

- `400 Bad Request` — невалидные данные (пустой продукт, отрицательный вес
  и т. п.), тело вида `{"detail": "..."}`.
- `500` — внутренняя ошибка сервера.

Фронтенд показывает пользователю текст из `detail`, если он есть, иначе
общее сообщение об ошибке.

## 2. Получить приёмы пищи за дату

`GET {API_BASE_URL}/meals?date=YYYY-MM-DD`

### Ответ 200 OK

Массив объектов приёмов пищи за указанную дату:

```json
[
  {
    "id": 1,
    "product": "Куриная грудка отварная",
    "weight_g": 150,
    "date": "2026-08-24",
    "calories": 248,
    "protein": 46.5,
    "fat": 5.4,
    "carbs": 0
  },
  {
    "id": 2,
    "product": "Рис отварной",
    "weight_g": 200,
    "date": "2026-08-24",
    "calories": 260,
    "protein": 5.4,
    "fat": 0.6,
    "carbs": 56
  }
]
```

Если приёмов пищи за дату нет — возвращается пустой массив `[]`
(не 404).

## Общие замечания

- Формат дат везде `YYYY-MM-DD` (ISO 8601, без времени) — совпадает со
  значением `<input type="date">` в браузере.
- Числовые поля — числа (не строки).
- CORS: бэкенд должен разрешать запросы с `null`/`file://` origin (при
  открытии `index.html` напрямую как файла) и с `http://localhost:*`
  (если фронтенд поднят через локальный сервер), иначе `fetch` в
  `app.js` будет падать — фронтенд обрабатывает эту ошибку без падения
  страницы (см. `apiRequest` в `app.js`).
- Данный контракт — только предположение фронтенда. Если реальный
  `api/API_CONTRACT.md` определяет другие пути, имена полей или формат —
  приоритет у него; этот файл тогда становится историческим черновиком.
