# Сессия 1 — Агенты: параллельная разработка трекера калорий четырьмя субагентами

- **Дата:** 2026-08-24
- **Ассистент:** Claude Code (Claude Sonnet 5)
- **Режим разрешений:** автоматическое выполнение инструментов (auto-accept) — в транскрипте нет ни одного запроса на подтверждение перед вызовом инструмента; при параллельной работе четырёх агентов с суммарно 207 вызовами инструментов ручное подтверждение каждого действия было бы непрактичным
- **Статус:** завершена
- **Этапы цикла:** 1. Диспетчеризация (4 параллельных субагента, зоны файлов), 2. Сведение результатов (README.md, REPORT.md), 3. Коммит

## Размышления

Ещё до диспетчеризации агент сам загрузил скилл `dispatching-parallel-agents` (из плагина Superpowers) — тот прямо предписывает: каждому субагенту точный фокус, самодостаточный контекст, явные ограничения и чёткий формат ожидаемого результата. Это напрямую отразилось в тексте промпта: у каждого из четырёх агентов — своя эксклюзивная зона файлов и явный запрет трогать чужую, что и позволило потом честно сказать «границы зон не нарушены ни одним агентом» — не как везение, а как следствие того, что правило было проговорено заранее.

Обнаружился интересный практический нюанс координации: текущий git-репозиторий на машине оказался инициализирован в корне всей домашней папки пользователя, а не в папке проекта — координатор это заметил и не стал туда коммитить, создав для «Трекер калорий» отдельный, изолированный репозиторий. Это тот самый класс проблем с окружением, которые не видны из текста задания, но реально всплывают в работе.

Самое содержательное расхождение вскрылось не в процессе, а из отчётов самих агентов: Агент B, читая (не редактируя) уже написанную модель Агента A, обнаружил несовпадение имён полей (`consumed_at`/`proteins`/`fats` в модели против `date`/`protein`/`fat` в его собственном модуле расчётов) и сам зафиксировал это как риск для координатора — не стал молча подстраиваться и не остановил работу, а просто написал об этом в своём отчёте. Похожим образом Агент A, закончив раньше, сверился с файлами-предположениями фронтенда и workflow и уже сообщил координатору, что именно нужно поправить фронтенду. Часть агентов, иначе говоря, начала координироваться друг с другом асинхронно, через письменные артефакты, ещё до того, как в дело вступил координатор.

Честный пробел, который агенты не скрыли: расчёт калорий «по весу от значения на 100 г» (Агент B) получился рабочим и протестированным, но два других агента (A и C) независимо решили хранить и вводить калории вручную — потому что в проекте не было справочника продуктов. Обе стороны рациональны сами по себе, но вместе дают разрыв между «есть код» и «код используется». Это не пришлось выяснять отдельно — про это написал сам Агент A в своём отчёте.

## Использованные инструменты

| Инструмент | Действие | Зачем |
|---|---|---|
| Skill (`dispatching-parallel-agents`) | Автозагрузка перед диспетчеризацией | Задаёт паттерн: фокусный, самодостаточный промпт на агента + явные границы |
| Agent ×4 (`run_in_background`) | Параллельный запуск Агентов A/B/C/D | Каждый — независимая зона файлов, без общего контекста друг с другом |

| Write | `README.md`, `REPORT.md` | Консолидированная документация по итогам всех четырёх агентов |
| mcp__ccd_session__mark_chapter | Разметка смены фазы работы | Отделить диспетчеризацию от сведения результатов в интерфейсе |

## Изменения в проекте

- Создан отдельный git-репозиторий в `Трекер калорий/` (не в унаследованном репозитории домашней папки).
- Созданы зоны: `models/`, `storage/`, `api/` (Агент A); `calculations/`, `tests/test_calculations.py` (Агент B); `frontend/` (Агент C); `workflows/` (Агент D).
- Контракты зафиксированы письменно: `api/API_CONTRACT.md`, `frontend/API_CONTRACT_ASSUMED.md`, `workflows/DEPENDENCIES_ASSUMED.md`, `calculations/README.md`.
- Написаны: `README.md` (как запустить), `REPORT.md` (разбор по зонам, конфликты, время/контекст).
- Коммит — 30 файлов, рабочее дерево чистое после проверки на мусор в `storage/` и `workflows/output/`.

## Финальный вердикт

Четыре независимых агента отработали параллельно без нарушения границ зон и без взаимной блокировки; координатор лично перепроверил сквозную интеграцию (не поверил на слово ни одному отчёту) — `pytest` 17/17, живой `uvicorn`, `curl`-цикл, дважды прогнанный workflow, фронтенд поверх живого API в браузере. Параллельный прогон занял ≈21 минуту против ≈58 минут при последовательном сложении времени всех агентов — выигрыш и по времени, и по контексту координирующей сессии (362 тыс. токенов внутренней работы агентов в неё не попали). Главный нерешённый вопрос — расчёт «по весу» не подключён к реальному пути данных — закрыт позже, отдельной веткой (см. сессию 4, worktrees).
