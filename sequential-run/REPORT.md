# Отчёт: тот же «Трекер калорий», один агент, последовательно

Та же задача, что в параллельном прогоне (см. [`../REPORT.md`](../REPORT.md)), но
выполненная без субагентов — одним агентом, одним потоком, одним и тем же контекстом,
от модели данных до фронтенда и workflow.

## Что сделано

Модель (`models/meal.py`) → хранилище на SQLite с атомарными транзакциями
(`storage/db.py`, `storage/meal_repository.py`) → CRUD API на FastAPI с валидацией
на границе (`api/main.py`, `api/schemas.py`) → расчёт калорий/БЖУ по весу и агрегация
день/неделя (`calculations/`) → 11 тестов (6 unit + 5 property-based на hypothesis,
все зелёные) → HTML-форма и таблица за день (`frontend/`) → идемпотентный дневной
отчёт (`workflows/daily_report.py`).

Интеграционная проверка (сделана лично, не «по описанию»): реальный CRUD-цикл через
`curl` (create/list/update/delete/404), `workflows/daily_report.py` запущен дважды
подряд против живого API (`recomputed` → `unchanged`, числа совпали), фронтенд открыт
в браузере поверх живого API — форма и таблица с итоговой строкой отработали без
ошибок в консоли.

## Никаких конфликтов контрактов — и это ожидаемо

В параллельном прогоне главным источником трения было несовпадение имён полей между
зонами, написанными разными агентами без общего контекста (`consumed_at` vs `date`,
`proteins` vs `protein`). Здесь этой проблемы в принципе не могло возникнуть: один
и тот же агент писал модель, хранилище, API, расчёты и фронтенд подряд, помня
названия полей, выбранные на предыдущем шаге. Это не «более качественная работа» —
это структурное следствие отсутствия параллелизма: нечему было расходиться.

По той же причине не воспроизведён и главный содержательный пробел параллельного
прогона (расчёт «по весу» не подключён к живому пути данных) — здесь `calculations/`
и `api/` писал один и тот же агент, поэтому решение «калории вводятся вручную» было
принято один раз и последовательно проведено через все слои, а не отдельно каждым.

## Время

|---|---|
| Старт | 06:28:06 |
| Готово к коммиту | 06:34:13 |

**Общая длительность прогона: ~6 минут 07 секунд** — от первого файла модели до
зелёных тестов, живого API, дважды прогнанного workflow и проверенного в браузере
фронтенда (плюс отдельно потраченное время на диагностику залипшего на порту 8000
процесса от предыдущего, параллельного прогона — см. раздел «Что пошло не по плану»).

## Контекст главной сессии

В отличие от параллельного прогона, где в контекст координатора попали только четыре
финальных отчёта субагентов (внутренняя работа каждого — десятки тысяч токенов —
осталась изолированной), здесь **вся** работа — чтение, запись каждого файла, каждый
`curl`, каждый прогон тестов, вся отладка с портом 8000 — прошла через один и тот же
контекст этой сессии. Точную разбивку токенов см. в ответе координатора в чате
(команда учёта использования сессии).

## Что пошло не по плану

Старый `uvicorn`-процесс из параллельного прогона (порт 8000) не завершился после
`pkill` в предыдущей задаче и продолжал слушать порт. Новый сервер этого прогона
молча падал при попытке забиндиться на тот же порт, а `curl` несколько запросов
подряд отвечал схемой **старого** проекта (`consumed_at`/`proteins`/`fats`), что на
секунду выглядело как баг в новом коде. Разобрался через `netstat` (нашёл PID
старого процесса) и `Stop-Process -Force` — после этого сервер поднялся и все
проверки прошли. Отдельный урок независимо от параллельно/последовательно: перед
повторным запуском сервера на фиксированном порту стоит проверять, не занят ли он
предыдущим прогоном.

## Сравнение с параллельным прогоном

| | Параллельно (4 субагента) | Последовательно (1 агент) |
|---|---|---|
| Границы контрактов | несовпадения из-за независимых решений, часть исправлена агентами самостоятельно | не возникли — один автор всех решений |
| Расчёт «по весу» подключён к API? | нет (изолированная, но не интегрированная возможность) | нет (то же архитектурное решение, принятое последовательно) |
| Итоговое время | ~21 мин (по самому долгому агенту) при ~58 мин суммарной работы агентов | см. таблицу выше |
| Контекст координирующей сессии | только 4 итоговых отчёта | вся работа целиком |
